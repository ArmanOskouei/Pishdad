# قرارداد مانیفست پلاگین: دسترسی‌ها، ویجت‌ها، انواع صفحه، جدول‌های دیتابیس

> مرجع پیاده‌سازی: `pishdad-core/backend/app/Services/Plugins/ManifestRegistry.php`
> (تک‌منبع ادغام هسته + مانیفست) — کنترلرها: `ManagerController::permissionsMatrix`،
> `WidgetSchemaController`، `LayoutController::pageTypes` — فرانت: `admin/managers?tab=roles`
> (ماتریس)، `admin/header-footer` (مودال تنظیمات)، `admin/blocks` (تب‌ها).
> بخش `db`: `PluginDbContract` (اعتبارسنجی اعلام) و `PluginMigrationRunner`
> (راستی‌آزمایی و بازنویسی migration) — قاعده‌ها از `PLUGIN-ECOSYSTEM-ARCHITECTURE.md`
> خط ۱۲۵.

پلاگین «اعلانی» است: کافی است در `manifest.json` یکی از کلیدهای زیر را بگذارید؛
هسته هنگام **فعال‌سازی** می‌خواند و در همان‌جای پنل قابل تنظیم می‌شود.
غیرفعال/حذف = ناپدید از ماتریس/پالت/تب‌ها (داده ذخیره‌شده قبلی دست‌نخورده می‌ماند).

## ۱. هوک `permissions` — ماژول دسترسی جدید

```json
{
  "permissions": [
    { "module": "blog", "title_fa": "بلاگ", "actions": ["view", "edit", "delete"] }
  ]
}
```

- `module`: الزامی، `^[a-z0-9_-]{2,40}$` (مثل `blog`). **خام بنویسید** — هسته
  خودش prefix اسلاگ را اضافه می‌کند.
- `title_fa`: الزامی‌نما — عنوان فارسی ستون «ماژول» در ماتریس نقش‌ها
  (`GET /api/v1/admin/permissions` → `modules[].{name,title_fa,source}`).
- `actions`: اختیاری، زیرمجموعه `view/edit/delete` (پیش‌فرض هر سه).
- هنگام فعال‌سازی، رکوردهای `plugin:{slug}:blog.view` و… در جدول permissions
  ساخته می‌شوند (`PluginController::ensurePermissions`) تا نقش همان‌جا تیک بخورد.
  **نام نهایی را در کد استفاده کنید**:
  `->middleware('perm:plugin:{slug}:blog.view')` (سوپرادمین همیشه عبور می‌کند).

  نکته: اگر خودتان prefix بنویسید، دوباره prefix می‌خورد
  (`plugin:slug:plugin:slug:blog.view`). پس `module` را **بدون** prefix بنویسید.
- چون نام نهایی namespaced است، ماژول افزونه هرگز با ماژول هسته تداخل
  نمی‌کند و دو افزونه با `module` هم‌نام هم پرمیشن مشترک نمی‌گیرند.
  در `admin.menu` برعکس است: آنجا `permission` نام **کامل** است و prefix لازم دارد.

## ۲. هوک `widgets` — ویجت هدر/فوتر جدید

```json
{
  "widgets": {
    "header": {
      "promo": {
        "title": "بنر تخفیف",
        "description": "نوار تخفیف بالای هدر.",
        "schema": {
          "type": "object",
          "properties": {
            "text": { "type": "string", "maxLength": 120 }
          }
        },
        "ui": { "labels": { "text": "متن بنر" } }
      }
    }
  }
}
```

- شکل هر ورودی دقیقاً مثل `config/widgets.php`: `title` + `description` +
  JSON Schema سبک + `ui.labels` (برچسب فارسی هر فیلد) و `ui.media_field`
  (کلیدی که با MediaPicker انتخاب می‌شود، مثل `media_id` در ویجت `logo`).
- فقط `type` جدید پذیرفته می‌شود (بازنویسی type هسته ممنوع).
- `GET /api/v1/admin/widgets/schema` همه را با `source: "plugin:{slug}"` می‌دهد و
  `PUT layouts/{area}` همان typeها را قبول می‌کند؛ فرانت مودال تنظیمات را با
  `SchemaForm` می‌سازد و برای type ناشناس fallback به JSON خام می‌دهد (نه حذف).
- قرارداد قالب‌ها هم همین است: `manifest` قالب فعال با همان شکل `widgets`
  خوانده می‌شود (`source: "theme:{slug}"`).

## ۳. هوک `page_types` — نوع صفحه جدید (تب بلوک‌ها)

```json
{
  "page_types": {
    "faq": {
      "title": "سوالات پرتکرار",
      "description": "صفحه FAQ پلاگین.",
      "default_blocks": [{ "type": "hero", "data": { "title": "سوالات پرتکرار" } }]
    }
  }
}
```

- تب‌های `admin/blocks` فقط از `GET layouts/page-types` می‌آیند (بدون هاردکد،
  حتی `blog`) و فقط typeهای `enabled !== false`؛ override هر type در
  `page_blocks:global:{type}` ذخیره می‌شود.
- `default_blocks` فقط typeهای `config/blocks.php` را می‌پذیرد.

## ۴. بخش `db` — جدول‌های دیتابیس افزونه

```json
{
  "db": {
    "tables": [
      { "name": "posts", "indexes": ["author_id", "slug"] },
      { "name": "comments" }
    ]
  }
}
```

پلاگین می‌گوید مالکِ کدام جدول‌هاست و هسته آن اعلام را در برابرِ متنِ
migrationهای خودِ بسته راستی‌آزمایی می‌کند (`PluginMigrationRunner`). بدون این
اعلام، هسته ناچار بود از روی متن کد حدس بزند چه جدول‌هایی در کار است — و حدسِ
غلط بی‌صدا به جدول‌های هسته می‌نویسد. پس اعلام کنید.

- **نام را خام بنویسید، بدون پیشوند.** در نمونهٔ بالا `slug` افزونه
  `my_plugin` است و جدولِ ساخته‌شده `my_plugin_posts` می‌شود؛ هسته پیشوند
  `{slug}_` را خودش اضافه می‌کند و همان را در migration بازنویسی می‌کند.
- **اگر خودتان پیشوند را بنویسید، خطا می‌خورید** (`db.table_already_prefixed`).
  جدولی که با `my_plugin_posts` اعلام شود `my_plugin_my_plugin_posts` می‌شود.
- `name` الزامی است و باید `^[a-z][a-z0-9_]{0,29}$` باشد (۱ تا ۳۰ نویسه، با حرف
  کوچک انگلیسی شروع شود، بعد فقط `a-z`، `0-9` و زیرخل). نام یکی از جدول‌های هسته
  هم پذیرفته نمی‌شود (`db.table_collides_core`) — هرچه با پیشوند به نام خودتان
  تبدیل می‌شود و به هسته دست نمی‌خورد.
- نام نهاییِ پیشوندشده نباید از **۴۰ نویسه** بلندتر باشد (`db.table_name_too_long`).
- `indexes` اختیاری است و سقف آن **۱۰ ایندکس در هر جدول** است — نه در کل
  افزونه. سقفِ کل یعنی ۱۰ ایندکس برای ۲۰ جدول، یعنی افزونه‌ای با بیست جدول فقط
  می‌توانست نیمی از آن‌ها را ایندکس کند.
- سقف کل **۲۰ جدول در هر افزونه** است (`db.too_many_tables`).
- **اسلاگی که نقطه یا خط تیره دارد اصلاً نمی‌تواند جدول داشته باشد**
  (`db.slug_not_table_safe`). دلیلش ساده است: نام نهایی شناسهٔ SQL می‌شود و
  `^[a-z0-9_]+$` باید در آن جا شود؛ برخلاف `slug` که نقطه و خط تیره را می‌پذیرد،
  نام جدول نمی‌پذیرد. یا اسلاگ را اصلاح کنید یا افزونه جدول نداشته باشد.
- **هر جدولی که migration به آن دست می‌زند باید اعلام شده باشد.** ارجاع به
  جدولِ اعلام‌نشده کل نصب را **fail-closed** رد می‌کند
  (`migration.undeclared_table`) — نه هشدار، نه نصبِ ناقص. این شامل
  `->constrained('users')` و `->index()->on('x')` هم می‌شود، چون هسته آن‌ها را
  هم ارجاع جدول می‌شمارد؛ پس قیدِ `foreignId` به جدول هسته، نصب را رد می‌کند.
  از این رو migration شما هیچ‌وقت نباید به جدولِ هسته اشاره کند.
- به همین دلیل، در migration هم نام خام بنویسید: `Schema::create('posts', …)`
  به `my_plugin_posts` بازنویسی می‌شود. هر فرمی که هسته نتواند با اطمینان
  حساب کند (SQL خام، `DB::raw`، نام پویا، `DB::connection`) هم کل نصب را رد
  می‌کند — چون بازنویسیِ ناتمام یعنی یک جدولِ بدون پیشوند که بی‌صدا به هسته
  می‌نویسد.
- **کل بخش `db` اختیاری است.** افزونه‌ای که جدول ندارد `db` را کلاً حذف
  می‌کند؛ `db` بدون `tables` بی‌معناست و خطا می‌گیرد (`db.no_tables`). کلید
  ناشناخته در `db` یا در هر آیتم `tables` پذیرفته نمی‌شود.

## ۵. احراز هویت در مسیرهای افزونه

> این بخش وجود دارد چون **انتقال یک هندلرِ حالت‌دار به افزونه** آن را آشکار کرد —
> و هیچ‌جا مکتوب نبود.

### catch-all هسته `auth:sanctum` ندارد

مسیرهای افزونه از یک catch-all واحد می‌آیند:

```
/api/v1/p/{slug}/{any?}
```

این catch-all فقط `PluginRouter` را صدا می‌زند. **هیچ middleware احراز هویتی روی
آن نیست**، چون هر افزونه ممکن است بخواهد مسیر عمومی داشته باشد (مثلاً صفحهٔ
وضعیت سرویس که نباید توکن بخواهد).

یعنی `$request->user()` **می‌تواند `null` باشد** و تصمیم با هندلر افزونه است.

### ⚠️ چرا این یک تلهٔ خاموش است

```php
// ❌ اگر کاربر لاگین نباشد، ErrorException می‌دهد
$request->user()->id
```

`PluginRouter` استثنا را می‌گیرد و **۵۰۰ عمومی** برمی‌گرداند — بدون سرنخ.
یعنی به‌جای «وارد شوید»، کاربر یک خطای بی‌معنا می‌بیند و **نویسندهٔ افزونه هیچ
پیامی برای اصلاح نمی‌گیرد**.

این یک خرابی واقعی است، نه فرضی: هندلری که دقیقاً همین‌طور نوشته شده بود ۵۰۰ داد،
در حالی که تست «انتظار ۴۰۱» داشت.

### قرارداد

هر هندلری که کاربر لازم دارد **باید خودش بررسی کند**:

```php
$user = $request->user();

if ($user === null) {
    return response()->json(['message' => 'وارد نشده‌اید.'], 401);
}
```

و `manifest.api.routes[].middleware` هم می‌تواند `auth:sanctum` اعلام کند.
**هر دو لایه خوب است:**

| لایه | چه می‌دهد | چه نمی‌دهد |
|---|---|---|
| `middleware` در مانیفست | محافظت اعلام‌شده، خوانا برای بازبین | اگر نویسنده فراموش کند، هیچ |
| بررسی در هندلر | همیشه کار می‌کند | اگر هر دو باشد، تکراری است |

### خطای کاربر باید از هندلر بیاید

`PluginRouter` این‌ها را عبور می‌دهد و به ۵۰۰ تبدیلشان نمی‌کند:

- `ValidationException` ⇒ **۴۲۲** با فهرست خطاها
- `HttpExceptionInterface` ⇒ همان کد (۴۰۳، ۴۰۴، …)

پس اگر می‌خواهی پیامِ خودت را بدهی، `abort(403, '…')` کافی است.

## ۶. قوانین مشترک

1. همه هوک‌ها اختیاری‌اند؛ مانیفست بدون آن‌ها معتبر است.
2. امضای Ed25519 و گردش تأیید سر جایش است (مورد ۶) — این قرارداد فقط
   «پس از فعال‌سازی» اعمال می‌شود.
3. داده‌های فعی پلاگین در یک نصب تک‌سایتی مشترک‌اند؛ `user_id` فقط سازنده/حسابرسی است و در خواندن فیلتر نمی‌شود.
4. افزونه می‌تواند جدول‌های core را **بخواند و بنویسد** — ولی نمی‌تواند آن‌ها را
   در `db.tables` اعلام کند. کار کردن روی دادهٔ هسته از داخل افزونه یک الگوی درست
   است، نه یک دور زدن.
5. **DDL افزونه** روی یک نقش جدا اجرا می‌شود و نامِ جدول‌های تازه در رجیستریِ
   core ثبت می‌شود. نگهبانِ دیتابیس هر نامِ ثبت‌نشده‌ای را رد می‌کند.
