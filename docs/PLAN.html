🎯 خلاصهٔ پروژه

ساخت یک CMS اختصاصی برای گرفتن سفارشات طراحی سایت. بک‌اند با Laravel (فقط API)، فرانت (سایت عمومی + پنل مدیریت) با Next.js. هر مشتری یک نصب جداگانه (تک‌مستاجر) دارد. هسته فقط مدیریت دارد و همه امکانات به‌صورت پلاگین اضافه می‌شود.

الگوی «پیش‌فرض فعال»

هر سایت یک پنل پیامک پیش‌فرض و یک درگاه پیش‌فرض انتخاب می‌کنه. هسته فقط اینترف‌یس رو صدا می‌زنه — هیچ سرویسی سخت‌کد نمی‌شه.

فرمت پلاگین (اعلانی + امضاشده)

plugin.zip
├── manifest.json          (نام، نسخه، وابستگی، hooks، schema بلوک، امضا)
├── backend/               (migrations، models، controllers، routes، اینترف‌یس‌ها)
└── blocks/                (schema بلوک‌ها برای رندرکننده عمومی)
  • امضای Ed25519 → فقط پلاگین‌های تأییدشده نصب می‌شن
  • استخراج امن ZIP (ضد zip-slip) + disable_functions در PHP
  • چرخهٔ حیات: install → register → activate → deactivate → upgrade → uninstall (با rollback)
  • schema-per-plugin در PostgreSQL → بدون تداخل جدول‌ها، حذف تمیز

استراتژی پلاگین (بازخورد نهایی — v1 باندل‌شده، v2 داینامیک)

  • v1: پلاگین‌ها = پکیج‌های Composer از قبل داخل تصویر هر نصب — فعال/غیرفعال فقط state. نصب = تغییر composer.json → commit → rebuild → activate
  • v2: داینامیک‌سازی (path repository) بعد از اثبات مدل
  • قانون سخت: فعال‌سازی = دیپلوی مجدد تصویر — هیچ فایل‌کپی رانتایمی
  • PLUGINS_SAFE_MODE=1: همه پلاگین‌ها رد + auto-disable روی exception (ضد deadlock)
  • هسته = اولین پلاگین (dogfooding): صفحات/فایل/تنظیمات به‌عنوان پلاگین ساخته می‌شن
  • Hookها روی خود Laravel (tagged container + Pipeline) به‌جای HookRegistry موازی

قدرت پلاگین (چک‌لیست)

  • ✅ جدول جدید به دیتابیس اضافه کنه
  • ✅ صفحهٔ سایت و صفحهٔ ادمین جدید بسازه
  • ✅ بلوک/ویجت قابل درگ‌اندروپ اضافه کنه
  • ✅ منو، داشبورد، تنظیمات، پروفایل (2FA) رو گسترش بده
  • ✅ از سرویس‌های پیامک/درگاه/روش ورود استفاده کنه

🔐 سوپرادمین + امنیت

  • سوپرادمین: توکن راه‌اندازی یکبارمصرف per-install (هش‌شده، با اولین ورود می‌سوزد، TTL کوتاه) + رمز شخصی که هرگز به مرکزی برنمی‌گرده. is_hidden، غیرقابل حذف، 2FA اجباری (TOTP + recovery codes هش‌شده)، لاگ جدا با hash-chain.
  • پروفایل مدیر: ایمیل + تلفن + رمز (هسته) + بخش‌های 2FA پلاگینی: پیامک + Authy.
  • لاگین مدیر: گام ۱ رمز → گام ۲ 2FA (روش‌های فعال پلاگینی).
  • امنیت API: rate limiting، sanitize (HTMLPurifier)، CSP/HSTS، CSRF، ضد بروت‌فورس.

امنیت پنل مرکزی (ارزشمندترین هدف)

  • کلید استاد چابکان: هرگز در دیتابیس حالت استراحت — تزریق runtime از Secret Manager + توکن‌های کوتاه‌عمر scope-limited + چرخش + لاگ/آلارم
  • توکن راه‌اندازی: بازتولید نیازمند step-up auth (2FA سخت‌افزاری اپراتور) + audit + kill-switch
  • بکاپ‌ها رمزنگاری‌شده (age/SOPS یا SSE-KMS) با کلید خارج از مرکزی + پاک‌سازی بکاپ تِنَنت حذف‌شده
  • ایزولاسیون تننت اثبات‌شده: کمترین دسترسی per-tenant (PG per-DB، MinIO IAM per-bucket) + تست رگرسیون ایزولاسیون در CI
  • Redis = غیرمرز امنیتی — هرگز سشن/داده حساس آنجا
  • پنل مرکزی: بدون Jodit/آپلود کاربر، DB/MinIO/Redis جدا، CSP سخت‌گیرتر، 2FA سخت‌افزاری

SSRF (کامل)

  • تابع egress مرکزی واحد: validate پس از resolve DNS + مسدودسازی IPv6 + ریدایرکت به‌ازای هر hop + پروتکل http(s)
  • مسدودسازی رنج‌های خصوصی/loopback/link-local/metadata (169.254.169.254)
  • remotePatterns سخت‌گیرانه برای next/image + presigned URL فقط سمت سرور

📐 سیستم قالب (کانفیگ‌محور — مثل وردپرس)

  • قالب = ZIP با theme.json (توکن‌های طراحی + چیدمان بلوک‌ها + CSS اختیاری)
  • چند قالب آپلودی + فعال‌سازی یکی + پیش‌نمایش + تغییر هر زمان
  • تعویض = عوض‌شدن ردیف فعال + revalidate → ظاهر جدید (داده‌ها دست نمی‌خوره)
  • پیاده‌سازی: BlockRegistry + BlockRenderer + CSS Variables + data-theme

مدل انتشار محتوا (تک‌منبع)

  • page_blocks = پیش‌نویس زنده — تنها منبع حقیقت محتوای در حال ویرایش
  • page_revisions = snapshot های immutable با revision_number صعودی
  • pages.published_revision_id = تنها اشاره‌گر + published_at + published_by
  • publish = یک تراکنش: insert ردیف جدید revision ← آپدیت اشاره‌گر ← reindex page_search
  • قفل همزمانی: pg_advisory_xact_lock (ضد race دو ادمین)
  • rollback/restore = ساخت revision جدید از قدیمی (تاریخچه حفظ می‌شود)

PG اختصاصی مشترک (~۱۵ مشتری) — پیکربندی

  • PgBouncer با pool_mode=transaction (۱۵×pool ۵-۱۰ = ۷۵-۱۵۰ → ~۵۰-۷۵ واقعی)
  • ⚠️ در transaction pooling: max_prepared_statements=0 یا PDO::ATTR_EMULATE_PREPARES=true
  • statement_timeout=30s + idle_in_transaction_session_timeout=60s
  • application_name=tenant_{id} + pg_stat_statements + آلارم ۸۰٪ مصرف
  • بکاپ per-DB + تست بازیابی ماهانه + SSL اجباری

🖥️ فرانت‌اند (Next.js)

یافته‌های نهایی فرانت (فاز ۳)

  • کش ISR اِفمِرال در چابکان: کانتینر stateless → .next/cache با هر deploy پاک می‌شه → cacheHandler روی Redis (prefix per-tenant) الزامی + prewarm
  • Next 15: fetch پیش‌فرض کش ندارد → next: { tags: [...] } صریح در هر fetch
  • ISR سه‌سطح: یا یک fetch ترکیبی با ۳ تگ (۱ round-trip) یا ۳ fetch موازی — تصمیم قبل از فاز ۳
  • پیش‌نمایش = مسیر جدا /preview + force-dynamic + توکن HMAC اجباری + noStore + CDN-Cache-Control no-store + robots Disallow
  • حلقه انتشار اول اثبات می‌شود: ادمین → انتشار → Laravel → وب‌هوک → revalidate → purge آروان → ISR
  • revalidate = دو نیمه یک لوله: revalidateTag + purge آروان از یک وب‌هوک واحد (تگ‌ها ≤۳۲ کاراکتر)
  • آپلود مستقیم MinIO نیازمند CORS روی باکت
  • بلوک‌های تعاملی: مرز use client جدا + next/dynamic + placeholder — هرگز کل درخت را کلاینت نکن

⏱️ طیف زمانی صورتحساب و تعلیق (Billing)

درگاه پرداخت فقط در پنل مرکزی نصب می‌شود (پلاگین PaymentGatewayInterface). دکمه پرداخت مشتری به مرکزی وصل می‌شود. پرداخت: ماهانه + تخفیف سالانه (۲۰٪).

فاز ۱ — یادآوری (D-7 تا D-0)

D-7 تا D-0: هر روز ایمیل + پیامک یادآوری (اگر پرداخت نشده باشد) → D-0 سررسید

فاز ۲ — سررسید (D-0)

✅ پرداخت شد → چرخه عادی ادامه
🔴 پرداخت نشد → غیرفعال‌سازی لحظه‌ای:
  • سایت عمومی ← مسدود + پیام «اشتراک هاست شما تمام شده است…» (بدون لینک پنل)
  • پنل ادمین ← فقط صفحه پرداخت فعال، بقیه امکانات غیرفعال
  • ایمیل + پیامک فوری: «سایت غیرفعال شد + ۷ روز تا حذف اطلاعات»

فاز ۳ — مهلت تعلیق (D-0 تا D+7)

D+4: به مشتری «۳ روز تا حذف کامل اطلاعات»
D+5: به مشتری «۲ روز تا حذف» + ⭐ به خودت «بکاپ لوکال بگیر»
D+6: به مشتری «۱ روز تا حذف» + ⭐ به خودت «فردا حذف؛ بکاپ آماده کن»
D+7: حذف کامل (DB + MinIO + منابع) + اعلان نهایی به خودت + مشتری

جدول اعلان‌ها

روزبه مشتریبه خودت
D-7 تا D-0هر روز یادآوری—
D-0 (پرداخت نشده)غیرفعال‌سازی + «۷ روز تا حذف»—
D+4«۳ روز تا حذف»—
D+5«۲ روز تا حذف»⭐ «بکاپ لوکال بگیر»
D+6«۱ روز تا حذف»⭐ «فردا حذف؛ بکاپ آماده کن»
D+7«اطلاعات حذف شد»«حذف انجام شد»

پیاده‌سازی تعلیق

  • تعلیق سطح اپلیکیشن (نه زیرساخت): سایت مسدود، پنل فقط پرداخت
  • suspension_mode در نصب مشتری → همه مسیرهای ادمین به‌جز /admin/subscription بسته می‌شوند (middleware)
  • Polling: نصب مشتری هر ۵–۱۰ دقیقه: GET /api/subscription-status?site_id=... (HMAC امضاشده)
  • Cron مرکزی همه اعلان‌ها/تعلیق/حذف را مدیریت می‌کند
  • متن قانونی (۷ روز، حذف اطلاعات، عدم مسئولیت) در قوانین/قرارداد هر نصب ثبت می‌شود

🚀 ماژول چابکان (مدیریت مرکزی + دیپلوی)

⚠️ تغییر مهم: از پنل مشتری «تنظیمات چابکان» حذف شد — مشتری هیچ‌وقت API key/چابکان را نمی‌بیند. همه عملیات چابکان از پنل مرکزی با کلید استاد انجام می‌شود.

دیپلوی خودکار

  • کلید استاد چابکان: فقط در پنل مرکزی (تزریق runtime از Secret Manager — هرگز در دیتابیس حالت استراحت)
  • بیلد لوکال (Next با standalone) → آپلود مستقیم → poll وضعیت → health check
  • جدول deployments با state machine + idempotency + rollback
  • الگوی استخر سرویس: سرویس‌های خالی از قبل آماده → رزرو + دیپلوی یک‌کلیکی
  • نمایش موجودی کیف پول + مدیریت سرویس‌ها از پنل مرکزی
  • اینترف‌یس ServiceProvisioner برای آینده (زمانی که API ساخت سرویس اضافه شود)
  • ⚠️ PoC چابکان = گیت سخت فاز ۰: ساخت → persistent paths → دیپلوی (سورس/آرتیفکت) → دامنه → SSL → health → آپدیت → rollback

استراتژی بیلد (بازخورد نهایی)

  • اولویت اول — git-build / آپلود سورس: اگر بیلد خودکار چابکان sharp را درست نصب کند (سقف ۱۰۰MB دور می‌زند). الزامات: package-lock + npm ci + Node پین‌شده
  • اولویت دوم — آرتیفکت prebuilt (بیلد لینوکسی CI): فقط اگر بیلد چابکان sharp را بشکند. standalone زیر ۱۰۰MB
  • هرگز بیلد per-tenant نکن — یک بیلد در هر نسخه
  • «کاناری» در چابکان شدنی نیست → ۱ تننت پایلوت → بچّه‌ای پلکانی → ۱۰۰٪

عملیات حیاتی (بازخورد نهایی)

  • هشدار موجودی کیف پول (زیر آستانه ۲ ماه) + هشدار خالی‌شدن استخر سرویس
  • Reconciliation job: اسکن GET /v1/services/ واقعی vs resource_registry → ترمیم/مارک شکست
  • Audit log هر فراخوانی چابکان + چرخش دوره‌ای کلید
  • /health دو سطح: liveness + readiness (DB/Redis/MinIO/queue/SSL) + escalation

⚠️ قیدهای مهم (یافته‌های متخصصان)

  1. دیتابیس اشتراکی چابکان بکاپ نداره → PG اختصاصی (حتی مشترک بین ۱۵ مشتری) لازم است
  2. CLI چابکان دستور ساخت سرویس نداره → PoC در فاز ۰؛ اگر ساخت از API نبود، استخر سرویس = عملیات دستی همیشه‌حاضر
  3. Google Fonts مسدوده → همه فونت‌ها محلی
  4. RTL باید از روز اول درست باشه (مهاجرت بعدی = بازنویسی)
  5. وب‌هوک revalidate → HMAC + nonce + timestamp + tag-based + purge آروان
  6. سوپرادمین → توکن یکبارمصرف per-install (می‌سوزد) — نه رمز ثابت/قابل بازیابی
  7. کش ISR در چابکان اِفمِراله → cacheHandler روی Redis الزامی
  8. sharp باینری native → بیلد لینوکسی همگام با رانتایم (بیلد ویندوز می‌شکنه)
  9. پنل مرکزی = ارزشمندترین هدف → کلید استاد/بکاپ/توکن‌ها با کلیدهای خارج از مرکزی + 2FA سخت‌افزاری
  10. ایزولاسیون تننت باید اثبات بشه → تست رگرسیون ایزولاسیون در CI
