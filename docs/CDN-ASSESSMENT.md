# ارزیابی: آیا CDN (آروان) لازم است؟ — `F0.12`

> **وضعیت:** ارزیابی فقط. **هیچ چیزی وصل نشده** و نباید بدون تصمیمِ مالک وصل شود.
> ردیف `F0.12` در `docs/TASKS.md` دستِ هماهنگ‌کننده است و این فایل فقط ورودیِ آن است.
>
> تاریخ ارزیابی: ۱۴۰۴/۰۷/۰۱

## خلاصهٔ یک‌خطی

**نه، الان ارزشش را ندارد.** کش از قبل **دقیقاً همان کاری را می‌کند که CDN برای
انجامش می‌فروشند، اما با یک مزیت که CDN ندارد: انتشارِ صفحه **آنی** اعمال می‌شود.
افزودن CDN در این وضعیت، خاصیتِ «منتشر کردم، همین حالا دیده شد» را خراب می‌کند بدون
اینکه جایگزینی برایش بسازیم.

## وضعیت فعلیِ کش (اندازه‌گیری‌شده، نه حدس)

| لایه | تنظیم | یعنی چه |
|---|---|---|
| صفحات عمومیِ سایت | `export const revalidate = 300` در Next.js (ISR) | HTML تا ۵ دقیقه کش است |
| همان صفحات | تگ‌های `pages` / `page:{slug}` / `site-chrome` / `site-homepage` / `site-status` | انتشار ⇒ باطال‌سازی **آنی** از راه وب‌هوک امضاشده |
| API عمومیِ صفحه | `Cache-Control: public, max-age=60, s-maxage=300` | لایهٔ مشترک ۵ دقیقه |
| API عمومیِ chrome/status | `Cache-Control: public, max-age=60` (بدون `s-maxage`) | ۶۰ ثانیه |
| پنلِ مدیریت | `no-store` در همه‌جا | هیچ‌وقت کش نمی‌شود |
| مدیا | MinIO با `AWS_URL` | روی دامنهٔ جدا، قابل کش |

**یعنی:** ۹۵٪ ترافیکِ یک سایتِ محتوایی (HTML + فایل‌های `/_next/static/*`) همین
الان پیش از رسیدن به بک‌اند، توسط خودِ Next.js سرو می‌شود.

## چرا CDN اینجا کم می‌آورد

### ۱. HTML از قبل کش است — CDN دومین لایهٔ کش اضافه می‌کند

ISR یعنی درخواست HTML به Node.js نمی‌رسد. اگر Arvan را جلوی آن بگذاریم، یک لایهٔ
کش دیگر اضافه می‌شود که **همان محتوا را نگه می‌دارد** و تنها کاری که می‌کند کاهش
محدودِ بار روی همان یک سرور است.

### ۲. ⭐ خطرِ درستی: وب‌هوک revalidate دیگر کافی نیست

این مهم‌ترین دلیل است. امروز وقتی مدیر صفحه را منتشر می‌کند:

```
مدیر → POST /pages/{id}/publish → RevalidateDispatcher → امضا → POST /api/revalidate
     → revalidateTag('pages') → پاک شدن فوری کش Next.js → بازدیدکنندهٔ بعدی محتوای تازه
```

اگر CDN جلوی Next.js باشد، `revalidateTag` فقط کشِ Next.js را پاک می‌کند. کشِ
Arvan همچنان HTML قدیمی نگه می‌دارد و **تا پاک شدن دستیِ CDN** (که یا باید API
اضافه کنیم، یا باید منتظر `s-maxage` بمانیم) محتوای کهنه سرو می‌شود.

یعنی دو راه داریم، و هر دو بد هستند:
- **API پاک‌سازی Arvan را اضافه کنیم** ⇒ یک سرویس بیرونیِ دیگر در مسیرِ بحرانیِ
  انتشار. اگر API‌شان خطا دهد یا rate-limit کند، انتشار باز هم «کار می‌کند» ولی
  کاربر محتوای کهنه می‌بیند — دقیقاً همان جایی که دروغ گفتن می‌شود.
- **صبر کنیم برای `s-maxage`** ⇒ خاصیتِ «انتشارِ آنی» را از دست می‌دهیم. این خاصیت
  الان یک تصمیمِ محصول است، نه یک اتفاق.

### ۳. مدلِ هر-نصبی با CDN ناسازگار است

این محصول **self-hosted per-install** است: هر مشتری نصب خودش را دارد. یعنی فعال‌کردن
CDN یعنی پیکربندی جداگانه برای هر نصب (دامنه، گواهی، کلید API پاک‌سازی، صورت‌حساب).
برای سازنده‌ای که مشتریِ عمده‌اش خودش سرور دارد، این یعنی پشتیبانیِ چند-مستاجری
روی چیزی که ذاتاً تک-مستاجری است.

### ۴. فایل‌های ایستا — تنها جایی که CDN واقعاً کمک می‌کند

`/_next/static/*` با هش در نام و کشِ بلندمدت سرو می‌شود. این‌ها کمترین تعدادِ ممکن
درخواست را دارند چون مرورگر یک‌بار می‌گیرد و تا تغییرِ deploy نگه می‌دارد. یعنی
بیشترین سودِ CDN، روی کم‌حجم‌ترین بخشِ ترافیک است.

## چه چیزی باید اول درست شود

پیش از هر بحث CDN، این دو (که ارزان‌تر و مؤثرترند):

1. **`cacheHandler` روی Redis فعال شود.** الان در `next.config.ts` **کامنت** است.
   بدون آن، کشِ ISR در حافظهٔ همان یک پروسهٔ Node است: با هر restart یا
   deploy، تمام صفحات از نو رندر می‌شوند. (خودِ فایل این را در کامنت نوشته و
   `cache-handler.mjs` هم آماده است.)
2. **تصمیم دربارهٔ `s-maxage` گرفته شود.** `max-age=60` بدون `s-maxage` یعنی
   «هر proxy بین کاربر و بک‌اند ۶۰ ثانیه کش می‌کند» — اگر بعداً CDN اضافه شود،
   همین عدد تعیین می‌کند کهنگی چقدر بد باشد. تصمیمِ آگاهانه بهتر از پیش‌فرض است.

## چه زمانی دوباره نگاه کنیم

CDN وقتی معنادار می‌شود که **یکی** از این‌ها صادقانه برقرار شود:

- ترافیک از یک سرورِ ایرانیِ تک، به نقطه‌ای رسیده که تأخیر برای بازدیدکنندهٔ خارج
  از ایران محسوس شده (یعنی مشتریِ بین‌المللی داریم).
- اندازه‌گیری نشان دهد TTFB صفحات عمومی گلوگاه است، نه رندر سمت سرور.
- `cacheHandler` فعال شده و باز هم scaling افقی لازم است.

اگر یکی از این‌ها رخ دهد، ترتیبِ درست این است: **اول** API پاک‌سازی Arvan را
بنویسیم و تست کنیم، **بعد** CDN را جلوی **فقط** `/_next/static/*` بگذاریم
(نه HTML) — چون فایل‌های ایستا پاک‌سازی لازم ندارند (هش در نام است) و پس ریسکِ
کهنگیِ انتشار را هم وارد بازی نمی‌کنند.

## جمع‌بندی برای مالک

| گزینه | توصیه |
|---|---|
| CDN روی HTML | ❌ نه — خاصیت انتشارِ آنی را خراب می‌کند |
| CDN روی `/_next/static/*` | ⏸️ فقط وقتی مشکلِ تأخیر داشته باشیم؛ کم‌ریسک‌ترین نقطهٔ شروع |
| `cacheHandler` روی Redis | ✅ اول این — ارزان‌تر، محلی، بدون سرویس بیرونی |
| تصمیم آگاهانه دربارهٔ `s-maxage` | ✅ قبل از هر CDN |

**پیشنهاد نهایی:** ردیف `F0.12` را **بسته** اعلام کنید با این متن که «ارزیابی انجام
شد؛ CDN در معماریِ فعلی توصیه نمی‌شود و دلیلش در `docs/CDN-ASSESSMENT.md` است». اگر
بعداً شرایط تغییر کرد، همین سند معیارِ بازبینی را هم دارد.
