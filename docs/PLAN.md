## 🎯 خلاصهٔ پروژه

ساخت یک **CMS اختصاصی** برای گرفتن سفارشات طراحی سایت. بک‌اند با **Laravel (فقط API)**، فرانت (سایت عمومی + پنل مدیریت) با **Next.js**. هر مشتری یک **نصب جداگانه (تک‌مستاجر)** دارد. هسته فقط مدیریت دارد و **همه امکانات به‌صورت پلاگین** اضافه می‌شود.


## 🧩 سیستم پلاگین (مهم‌ترین بخش — مثل وردپرس ولی امن‌تر)

### ۳ دسته پلاگین

| دسته | اینترف‌یس هسته | مثال |
|---|---|---|
| **سرویس‌دهنده** | `SmsProviderInterface`، `PaymentGatewayInterface` | ملی‌پیامک، ippanel، زرین‌پال، بانک ملی |
| **امکاناتی** | `FeatureProviderInterface` | بلاگ، نمونه‌کار، فروشگاه، کاربران |
| **احراز/تأیید** | `AuthMethodInterface`، `VerifyLevelInterface` | ورود OTP، ایمیل+رمز، شاهکار |

### الگوی «پیش‌فرض فعال»

هر سایت یک **پنل پیامک پیش‌فرض** و یک **درگاه پیش‌فرض** انتخاب می‌کنه. هسته فقط اینترف‌یس رو صدا می‌زنه — هیچ سرویسی سخت‌کد نمی‌شه.

### فرمت پلاگین (اعلانی + امضاشده)

```
plugin.zip
├── manifest.json          (نام، نسخه، وابستگی، hooks، schema بلوک، امضا)
├── backend/               (migrations، models، controllers، routes، اینترف‌یس‌ها)
└── blocks/                (schema بلوک‌ها برای رندرکننده عمومی)
```

- امضای **Ed25519** → فقط پلاگین‌های تأییدشده نصب می‌شن
- استخراج امن ZIP (ضد zip-slip) + `disable_functions` در PHP
- چرخهٔ حیات ۴مرحله‌ای: `install → register → activate → uninstall` (با rollback)
- **schema-per-plugin** در PostgreSQL → بدون تداخل جدول‌ها، حذف تمیز

### استراتژی پلاگین (بازخورد نهایی — v1 باندل‌شده، v2 داینامیک)
- **v1:** پلاگین‌ها = **پکیج‌های Composer از قبل داخل تصویر** هر نصب — فعال/غیرفعال فقط state در config/DB. نصب = تغییر composer.json → commit → rebuild → activate. (۹۰٪ پیچیدگی نصب رانتایم حذف)
- **v2:** داینامیک‌سازی (کامپوننت path repository در deploy) بعد از اثبات مدل
- **قانون سخت:** فعال‌سازی = دیپلوی مجدد تصویر — هیچ فایل‌کپی رانتایمی
- **PLUGINS_SAFE_MODE=1** در env: همه پلاگین‌ها رد می‌شن + auto-disable روی exception در boot (ضد deadlock پلاگین خراب)
- **هسته = اولین پلاگین (dogfooding):** صفحات/فایل/تنظیمات به‌عنوان پلاگین ساخته می‌شن تا سیستم پلاگین خودش را اثبات کنه
- **Hookها روی خود Laravel** (tagged container + Pipeline) به‌جای HookRegistry موازی

### نقاط اتصال (Hookهای اینترف‌یسمحور — ۱۲ مورد)

```
AdminMenu / AdminRoute / DashboardWidget / SettingsTab
SiteRoute / Block / SiteHeaderFooter / ProfileSection
SmsProvider / PaymentGateway / AuthMethod / VerifyLevel
```

### قدرت پلاگین (چک‌لیست)

- ✅ جدول جدید به دیتابیس اضافه کنه
- ✅ صفحهٔ سایت و صفحهٔ ادمین جدید بسازه
- ✅ بلوک/ویجت قابل درگ‌اندروپ اضافه کنه
- ✅ منو، داشبورد، تنظیمات، پروفایل (2FA) رو گسترش بده
- ✅ از سرویس‌های پیامک/درگاه/روش ورود استفاده کنه

## 🔐 سوپرادمین + امنیت

- **سوپرادمین:** توکن راه‌اندازی **یکبارمصرف** per-install (هش‌شده، با اولین ورود می‌سوزد، TTL کوتاه) + رمز شخصی که هرگز به مرکزی برنمی‌گرده. `is_hidden` (در لیست مدیران نیست)، غیرقابل حذف، 2FA اجباری (TOTP + recovery codes هش‌شده)، لاگ جدا با hash-chain.
- **پروفایل مدیر:** ایمیل + تلفن + رمز (هسته) + **بخش‌های 2FA پلاگینی**: پیامک (اگر پلاگین پیامک فعال) + Authy (اگر در پروفایل فعال باشه).
- **لاگین مدیر:** گام ۱ رمز (هسته) → گام ۲ 2FA (روش‌های فعال پلاگینی).
- امنیت API: rate limiting، sanitize خروجی Jodit (HTMLPurifier)، هدرهای CSP/HSTS، CSRF، لاگین ضد بروت‌فورس.

### امنیت پنل مرکزی (ارزشمندترین هدف — بازخورد نهایی)
- **کلید استاد چابکان:** هرگز در دیتابیس در حالت استراحت — تزریق runtime از Secret Manager + توکن‌های کوتاه‌عمر scope-limited (فقط-provisioning جدا از فقط-read) + چرخش خودکار + لاگ/آلارم استفاده
- **توکن راه‌اندازی:** بازتولید نیازمند **step-up auth** (2FA سخت‌افزاری اپراتور) + ثبت audit + kill-switch برای ابطال یک‌جا
- **بکاپ‌ها رمزنگاری‌شده** (age/SOPS یا SSE-KMS) با کلیدی خارج از مرکزی + پاک‌سازی بکاپ تِنَنت حذف‌شده
- **ایزولاسیون تننت اثبات‌شده** (نه ادعا): اعتبارنامه کمترین دسترسی per-tenant (PG per-DB، MinIO IAM per-bucket) + تست‌های رگرسیون ایزولاسیون خودکار در CI
- **Redis = غیرمرز امنیتی** (در threat model صریح) — هرگز سشن/داده حساس آنجا
- **پنل مرکزی** روی کدبیس مشترک → دیپلوی سخت‌گیرانه‌تر: بدون Jodit/آپلود کاربر، دیتابیس/MinIO/Redis جدا، CSP سخت‌گیرتر، 2FA سخت‌افزاری

### SSRF (کامل)
- تابع egress مرکزی واحد: validate **پس از resolve DNS** (نه فقط رشته hostname) + مسدودسازی IPv6 + ریدایرکت به‌ازای هر hop + محدودیت پروتکل http(s)
- مسدودسازی رنج‌های خصوصی/loopback/link-local/metadata (169.254.169.254)
- `remotePatterns` سخت‌گیرانه برای next/image + presigned URL فقط سمت سرور

## 🗄️ دیتابیس (PostgreSQL — ICU فارسی)

| جدول | نکات کلیدی |
|---|---|
| `pages` + `page_blocks` | متادیتا جدا + بلوک‌های رابطه‌ای با JSONB (منبع حقیقت، نه HTML تک‌ستونه) |
| `revisions` | تاریخچه نسخه صفحات |
| `audit_logs` | لاگ ادمین (کی/کی/چه/کیف) |
| `redirects` | 301 خودکار |
| `settings` | value JSONB + PK ترکیبی (group, key) |
| `media`, `tickets`, `roles/permissions` | پایه |
| جداول پلاگین | schema جدا به‌ازای پلاگین |

**نکات فارسی:** Collation ICU `fa-IR`، نرمال‌سازی نیم‌فاصله/ی-ک، تاریخ فقط UTC (جلالی در لایه نمایش)، FTS با `simple` + `pg_trgm`.

### مدل انتشار محتوا (اصلاح‌شده — تک‌منبع)
- `page_blocks` = **پیش‌نویس زنده** (workspace) — تنها منبع حقیقت محتوای در حال ویرایش
- `page_revisions` = **snapshot های immutable** با `revision_number` صعودی
- `pages.published_revision_id` = **تنها اشاره‌گر** + `published_at` + `published_by`
- publish = یک تراکنش: insert ردیف جدید revision ← آپدیت اشاره‌گر ← reindex page_search
- قفل همزمانی: `pg_advisory_xact_lock` در publish (ضد race دو ادمین)
- rollback/restore = ساخت revision جدید از قدیمی (تاریخچه حفظ می‌شود)

### ماتریس مالکیت داده (هسته vs مرکزی)
| جدول | دیتابیس | منبع حقیقت |
|---|---|---|
| pages, page_blocks, media, tickets, orders... | دیتابیس مشتری (tenant) | tenant |
| plans, invoices, payments, chabokan_services, deployments, clients | دیتابیس مرکزی | central |
| subscription_status (در نصب مشتری) | دیتابیس tenant | **کش محلی** — polling از مرکزی |

### PG اختصاصی مشترک (~۱۵ مشتری) — پیکربندی
- **PgBouncer با pool_mode=transaction** (۱۵ مشتری × pool ۵-۱۰ = ۷۵-۱۵۰ → ~۵۰-۷۵ کانکشن واقعی)
- ⚠️ در transaction pooling: `max_prepared_statements=0` در PgBouncer یا `PDO::ATTR_EMULATE_PREPARES=true`
- `statement_timeout=30s` + `idle_in_transaction_session_timeout=60s` (حفاظت از noisy neighbor)
- `application_name=tenant_{id}` در connection string هر مشتری → تشخیص در pg_stat_activity
- `pg_stat_statements` + آلارم در ۸۰٪ مصرف کانکشن و کوئری‌های بالای ۵ ثانیه
- بکاپ per-DB (نه dumpall) + تست بازیابی ماهانه + SSL اجباری

## 🖥️ فرانت‌اند (Next.js)

- **RTL از روز اول** (logical properties) + فونت محلی Vazirmatn (گوگل فونت در ایران مسدوده)
- **سایت:** ISR سه‌سطح (قالب/لایه‌اوت/محتوا) + `next/image` AVIF + Three.js/GSAP فقط با dynamic/ssr:false
- **پنل /admin:** path در همون اپ + Route Group جدا + RBAC (کارفرما/مشتری) + Jodit
- **قالب:** CSS Variables + BlockRenderer واحد
- `output: 'standalone'` + CDN ایرانی استاتیک

### یافته‌های نهایی فرانت (باید در فاز ۳ اعمال شود)
- **کش ISR اِفمِرال در چابکان:** کانتینر stateless → `.next/cache` با هر restart/deploy پاک می‌شه → **cacheHandler سفارشی روی Redis** (کلید prefix شده per-tenant) الزامی است + prewarm بعد از deploy
- **Next 15: fetch پیش‌فرض کش ندارد** → `next: { tags: [...] }` صریح در هر fetch (وگرنه ISR وجود ندارد)
- **ISR سه‌سطح:** یا یک fetch ترکیبی با ۳ تگ (۱ round-trip) یا ۳ fetch موازی — تصمیم قبل از فاز ۳
- **پیش‌نمایش = مسیر جدا `/preview`** با force-dynamic + **توکن HMAC اجباری** (الا درز draft) + `noStore` + `CDN-Cache-Control: no-store` در middleware + robots.txt Disallow
- **حلقه انتشار اول اثبات می‌شود:** ادمین → انتشار → Laravel → وب‌هوک → revalidate → purge آروان → ISR (قبل از ساخت قالب کامل)
- **revalidate = دو نیمه یک لوله:** `revalidateTag` سمت Next + purge API آروان — از یک وب‌هوک واحد (تگ‌ها ≤۳۲ کاراکتر، prefixدار)
- **آپلود مستقیم MinIO نیازمند CORS** روی باکت (AllowOrigin = دامنه ادمین + AllowHeaders PUT)
- **بلوک‌های تعاملی:** مرز `use client` در کامپوننت جدا با `next/dynamic` + placeholder ارتفاع ثابت — هرگز کل درخت را کلاینت نکن

## 💳 مدل کسب‌وکار اشتراکی + تیربندی هزینه

> چون مدل **اشتراکی** انتخاب شد، مشتری مستقیم به چابکان وصل نمی‌شود — همه‌چیز از حساب مرکزی تو (کلید استاد) مدیریت می‌شود. جزئیات کامل در `COST-TIERING.md`.

### معماری ۳ تیره

| تیر | مخاطب | PostgreSQL | MinIO | Redis |
|---|---|---|---|---|
| **Budget** | مشتری کوچک (پیش‌فرض) | PG اختصاصی مشترک (~۱۵ مشتری، ۱ دیتابیس per مشتری) | مرکزی + باکت per مشتری | مرکزی + prefix per مشتری |
| **Standard** | مشتری متوسط | PG اختصاصی per مشتری | اختصاصی | اختصاصی |
| **Enterprise** | مشتری بزرگ | PG اختصاصی + replica | اختصاصی + versioning | اختصاصی |

### هزینه per مشتری (ماهانه، تومان)

| مؤلفه | Budget (~۱۵ مشتری) | Standard | Enterprise |
|---|---|---|---|
| هاست Laravel | ۵۵۰,۰۰۰ | ۵۵۰,۰۰۰ | ۱,۰۰۰,۰۰۰ |
| هاست Next.js | ۵۵۰,۰۰۰ | ۵۵۰,۰۰۰ | ۱,۰۰۰,۰۰۰ |
| PostgreSQL | ۱۳۳,۰۰۰ (۲M÷۱۵) | ۲,۰۰۰,۰۰۰ | ۲,۰۰۰,۰۰۰ + replica |
| Redis | ۲۰,۰۰۰ (۳۰۰K÷۱۵) | ۳۰۰,۰۰۰ | ۳۰۰,۰۰۰ |
| MinIO | ۲۷,۰۰۰ (۴۰۰K÷۱۵) | ۴۰۰,۰۰۰ | ۴۰۰,۰۰۰ |
| **جمع/ماه** | **~۱,۲۸۰,۰۰۰** | **~۳,۸۰۰,۰۰۰** | **~۴,۷۰۰,۰۰۰** |
| **جمع/سال** | **~۱۵.۴M** | **~۴۵.۶M** | **~۵۶M** |

### نکات کلیدی تیربندی

- کانتینرهای اپ (Laravel + Next) **اختصاصی per مشتری** می‌مانند (برای دامنه/SSL ایزوله) — تهیه‌کننده: تو
- PG اختصاصی مشترک → بکاپ خودکار دارد (⚠️ PG **اشتراکی** چابکان بکاپ ندارد → فقط اختصاصی مشترک)
- `pg_dump` شبانه به MinIO مرکزی (بکاپ دوم، retention ۱۴ روز)
- مهاجرت Budget → Standard = «دکمه ارتقا» در پنل مرکزی (pg_dump → restore بدون Downtime)
- **بکاپ تست بازیابی ماهی یک‌بار** — بکاپِ بازیابی‌نشده = بکاپ نیست

### مقایسه با cPanel (۱۰ مشتری، سالانه)

| مدل | هزینه سالانه | پشتیبانی ISR/پلاگین رانتایم؟ |
|---|---|---|
| چابکان تیربندی (Budget) | ~۱۴۶M | ✅ |
| چابکان هر مشتری جدا | ~۲۸۲M | ✅ |
| cPanel اختصاصی (۲ سرور) | ~۶۰M | ❌ (Next.js ISR نمی‌شه — فقط PHP) |

> ⚠️ **نکته حیاتی:** فرانت Next.js با ISR به Node.js نیاز دارد — هاست‌های cPanel عادی فقط PHP اجرا می‌کنند. پس cPanel فقط وقتی منطقی است که از ISR/پلاگین رانتایم صرف‌نظر کنیم.

## ⏱️ طیف زمانی صورتحساب و تعلیق (Billing)

> درگاه پرداخت فقط در **پنل مرکزی** نصب می‌شود (پلاگین `PaymentGatewayInterface`). دکمه پرداخت مشتری به مرکزی وصل می‌شود. پرداخت: **ماهانه + تخفیف سالانه (۲۰٪)**.

### فاز ۱ — یادآوری (۷ روز قبل از سررسید)

```
D-7 ── ایمیل + پیامک: «فاکتور شما ۷ روز دیگر سررسید می‌شود»
D-6 ── ایمیل + پیامک
D-5 ── ایمیل + پیامک
...  ── (هر روز، تا روز سررسید، اگر پرداخت نشده باشد)
D-0 ── ⏰ روز سررسید
```

### فاز ۲ — سررسید (D-0)

```
✅ پرداخت شد → چرخه عادی ادامه

🔴 پرداخت نشد → غیرفعال‌سازی لحظه‌ای:
  • سایت عمومی ──→ مسدود + پیام «اشتراک هاست شما تمام شده است…»
                  (بدون نمایش لینک پنل مدیریت)
  • پنل ادمین ──→ فقط صفحه پرداخت فعال، بقیه امکانات غیرفعال
  • ایمیل + پیامک فوری: «سایت غیرفعال شد + ۷ روز تا حذف اطلاعات»
```

### فاز ۳ — مهلت تعلیق (D-0 تا D+7)

```
D+4 ── ایمیل + پیامک به مشتری: «۳ روز تا حذف کامل اطلاعات»
D+5 ── ایمیل + پیامک به مشتری + ⭐ اعلان به خودت: «مشتری X در روز D+7 حذف می‌شود، بکاپ لوکال بگیر»
D+6 ── ایمیل + پیامک به مشتری + ⭐ اعلان مجدد به خودت: «فردا حذف می‌شود، بکاپ لوکال آماده کن»
D+7 ── ⚠️ حذف کامل (دیتابیس + MinIO + منابع) + اعلان نهایی به خودت + مشتری
```

### جدول اعلان‌ها (خلاصه)

| روز | به مشتری | به خودت |
|---|---|---|
| D-7 تا D-0 | هر روز یادآوری | — |
| D-0 (پرداخت نشده) | غیرفعال‌سازی + «۷ روز تا حذف» | — |
| D+4 | «۳ روز تا حذف» | — |
| D+5 | «۲ روز تا حذف» | ⭐ «بکاپ لوکال بگیر» |
| D+6 | «۱ روز تا حذف» | ⭐ «فردا حذف؛ بکاپ آماده کن» |
| D+7 | «اطلاعات حذف شد» | «حذف انجام شد» |

### پیاده‌سازی تعلیق

- **تعلیق سطح اپلیکیشن** (نه زیرساخت): سایت عمومی مسدود، پنل فقط پرداخت
- `suspension_mode` در نصب مشتری → همه مسیرهای ادمین به‌جز `/admin/subscription` بسته می‌شوند (middleware)
- **Polling:** نصب مشتری هر ۵–۱۰ دقیقه از پنل مرکزی: `GET /api/subscription-status?site_id=...` (HMAC امضاشده)
- **Cron مرکزی** (نه داخل هر نصب) همه اعلان‌ها/تعلیق/حذف را مدیریت می‌کند
- متن قانونی (۷ روز، حذف اطلاعات، عدم مسئولیت) در قوانین/قرارداد هر نصب ثبت می‌شود

## 🚀 ماژول چابکان (مدیریت مرکزی + دیپلوی)

> ⚠️ **تغییر مهم:** از پنل مشتری «تنظیمات چابکان» **حذف شد** — مشتری هیچ‌وقت API key/چابکان را نمی‌بیند. همه عملیات چابکان از **پنل مرکزی** با **کلید استاد** انجام می‌شود.

### معماری جدید

```
مشتری (cms-core)                  پنل مرکزی (central-plugin)
├── /admin/subscription            ├── مدیریت چابکان (کلید استاد)
│     (وضعیت + فاکتور + پرداخت)    ├── ساخت/دیپلوی/مدیریت سرویس‌ها
├── suspension_mode middleware     ├── مدیریت مشتریان + تیر + دامنه
├── صفحه تعلیق عمومی               ├── Billing (پلن/فاکتور/درگاه/Cron)
└── Polling از مرکزی (۵-۱۰ دقیقه)   └── تعلیق/بازگشایی/حذف
```

### Provisioning (تهیه زیرساخت)

| سرویس | تهیه‌کننده | اختصاصی/اشتراکی |
|---|---|---|
| هاست Laravel | **تو** (per مشتری) | اختصاصی |
| هاست Next.js | **تو** (per مشتری) | اختصاصی |
| PostgreSQL | تو | اشتراکی (~۱۵ دیتابیس) یا اختصاصی برای بزرگ‌ها |
| MinIO + Redis | تو | مرکزی اشتراکی |

### دیپلوی خودکار

- کلید استاد چابکان: **فقط در پنل مرکزی** (تزریق runtime از Secret Manager — هرگز در دیتابیس حالت استراحت) — هرگز به نصب مشتری نمی‌رسد
- بیلد لوکال (Next با standalone) → آپلود مستقیم → poll وضعیت → health check
- جدول `deployments` با state machine + idempotency + rollback
- **الگوی استخر سرویس:** سرویس‌های خالی از قبل آماده → نصب مشتری = رزرو + دیپلوی یک‌کلیکی
- نمایش موجودی کیف پول + مدیریت سرویس‌ها (start/stop/restart/resize) از پنل مرکزی
- **آینده‌نگری:** اینترف‌یس `ServiceProvisioner` — وقتی چابکان ساخت سرویس رو به API اضافه کرد، فقط یه درایور جدید
- ⚠️ **PoC چابکان = گیت سخت فاز ۰ (نه فاز ۱۰):** ساخت → persistent paths → دیپلوی (سورس و آرتیفکت) → دامنه → SSL → health → start/stop/resize → آپدیت → rollback → اندازه‌گیری (زمان، حجم، sharp، هزینه)

### استراتژی بیلد (بازخورد نهایی)
- **اولویت اول — git-build / آپلود سورس:** اگر بیلد خودکار چابکان sharp را درست نصب کند (سقف ۱۰۰MB دور می‌زند + یک سورس = منبع حقیقت). الزامات: package-lock کامیت‌شده + npm ci + Node پین‌شده + sharp dependency معمولی
- **اولویت دوم — آرتیفکت prebuilt (بیلد لینوکسی CI):** فقط اگر بیلد چابکان sharp را بشکند. خروجی standalone زیر ۱۰۰MB
- **هرگز بیلد per-tenant نکن** — یک بیلد در هر نسخه
- **«کاناری» در چابکان شدنی نیست** → بازتعریف: ۱ تننت پایلوت → بچّه‌ای پلکانی (۵تایی) → ۱۰۰٪، با rollback = دیپلوی نسخه قبلی

### عملیات حیاتی (بازخورد نهایی)
- **هشدار موجودی کیف پول** (زیر آستانه ۲ ماه) + **هشدار خالی‌شدن استخر سرویس** — چون شارژ/ساخت دستی است
- **Reconciliation job:** اسکن دورهای `GET /v1/services/` واقعی vs resource_registry → ترمیم/مارک شکست‌خورده (قلب idempotency)
- **Audit log هر فراخوانی چابکان** (کی/کی/چه/نتیجه) + چرخش دوره‌ای کلید
- **/health دو سطح:** liveness + readiness (DB/Redis/MinIO/queue/SSL) + escalation به تلگرام/ایمیل

## 📐 اصل «Definition of Done» برای هر فاز

هر فاز فقط وقتی «تمام» است که این‌ها در آن فاز پیاده‌شده باشند (نه فاز ۱۱):

| چک‌لیست امنیتی/عملیاتی | توضیح |
|---|---|
| **Rate limit** | روی هر auth endpoint و API عمومی |
| **SSRF guard** | تابع egress مرکزی: validate پس از resolve DNS (شامل IPv6 + DNS rebinding) + مسدودسازی رنج‌های خصوصی/متادیتا + `remotePatterns` سخت‌گیرانه برای next/image |
| **Sanitize** | HTMLPurifier (سقف عمق/حجم) روی هر ورودی HTML |
| **Audit log hash-chain** | از روز اول + لنگر دوره‌ای به MinIO/مرکزی |
| **Observability** | لاگ متمرکز + correlation ID + heartbeat/health به مرکزی |
| **بکاپ** | هر فازی که داده می‌سازد → بکاپ + تست بازیابی |
| **RTL** | logical properties در هر کامپوننت جدید (گیت code-review) |

## ⚠️ قیدهای مهم (یافته‌های متخصصان)

1. **دیتابیس اشتراکی چابکان بکاپ نداره** → هر مشتری Production به دیتابیس اختصاصی (حتی مشترک بین ۱۵ مشتری) نیاز داره
2. **CLI چابکان دستور ساخت سرویس نداره** → PoC در فاز ۰؛ اگر ساخت سرویس از API نبود، «اتوماسیون کامل» سقف داره و استخر سرویس = عملیات دستی همیشه‌حاضر
3. **Google Fonts مسدوده** → همه فونت‌ها محلی
4. **RTL باید از روز اول** درست باشه (مهاجرت بعدی = بازنویسی)
5. **وب‌هوک revalidate** → HMAC + nonce + timestamp + tag-based + purge آروان (نه کلید ساده)
6. **سوپرادمین** → توکن یکبارمصرف per-install (می‌سوزد) — نه رمز ثابت، نه رمز قابل بازیابی (هر ۶ متخصص تأکید کردن)
7. **کش ISR در چابکان اِفمِراله** → cacheHandler روی Redis الزامی (هر deploy پاک می‌شه)
8. **sharp باینری native** → بیلد باید لینوکسی همگام با رانتایم باشد (بیلد ویندوز روی چابکان می‌شکنه)
9. **پنل مرکزی = ارزشمندترین هدف** → کلید استاد/بکاپ‌ها/توکن‌ها با کلیدهای خارج از مرکزی + 2FA سخت‌افزاری اپراتور
10. **ایزولاسیون تننت باید اثبات بشه** → تست رگرسیون ایزولاسیون در CI (PG per-DB، MinIO per-bucket IAM)
