# بخش ۱ — پلاگین چیست و چه می‌تواند

## تعریف عملیاتی

پلاگین یک بستهٔ ZIP است که **دو بخش دارد**: کد PHP (بک‌اند) و توضیحات ساختاری (فرانت). و **دقیقاً سه چیز** می‌تواند به سایت اضافه کند:

| بُعد | توضیح |
|---|---|
| **۱. مسیر API** | endpointهای خودش زیر `/api/v1/p/{slug}/…` |
| **۲. داده** | جدول‌های خودش با prefix `{slug}_` |
| **۳. نقاط اتصال UI** | آیتم منو، ویجت، بلوک، صفحه، فرم تنظیمات |

**هر چیز دیگری ممنوع است.** مخصوصاً:
- ⛔ فایل PHP در پوشه‌های هسته (هیچ فایلی وارد `app/` نمی‌شود)
- ⛔ کامپوننت React یا JavaScript (در مرورگر مدیر اجرا می‌شد ⇒ تصاحب کامل پنل)
- ⛔ اجرای `build` (تک‌نویسنده روی `.next` ⇒ build نیمه‌کاره یعنی صفحهٔ سفید برای کل پنل)
- ⛔ دسترسی به جدول‌های هسته
- ⛔ خواندن `.env` یا توکن‌های Sanctum

## چرا این محدودیت‌ها؟

این‌ها خودخودی نیستند. هرکدام یک ریسک مشخص را می‌بندند:

| ممنوعیت | ریسکی که می‌بندد |
|---|---|
| فایل در پوشهٔ هسته | هر آپدیت پیشداد باید ۵۰۰ عملیات فایل را تکرار کند؛ rollback تراکنشی ندارد؛ دو نسخه نمی‌توانند هم‌زیستی کنند |
| کامپوننت React | کد در مرورگر مدیر اجرا می‌شود و از همان `/api/proxy` که کوکی نشست را حمل می‌کند، دسترسی کامل ادمین می‌گیرد |
| build در runtime | `next build` چند دقیقه طول می‌کشد و `next start` از `.next` سرو می‌کند ⇒ build نیمه‌کاره = کل پنل سفید |
| جدول هسته | یک پلاگین مخرب `DROP TABLE users` می‌زند |

## صادقانه‌ترین حرف

> **هیچ پلاگین لاراولی درون‌فرایندی، امنیت مرزی ایجاد نمی‌کند.** PHP در حال اجرا هر کاری می‌تواند بکند.

هر کنترلی که داریم **کاهش سطح حمله است، نه حذف آن.** باقی‌مانده‌ها:

| خطر باقی‌مانده | چرا می‌ماند |
|---|---|
| خواندن `.env` با `getenv()` | سهمهٔ فرایند جدا عملی نیست |
| دسترسی شبکهٔ بی‌محافظ | `PluginContext::httpClient()` + allowlist دامنه (هنوز ساخته نشده) |
| DoS با حلقهٔ بی‌نهایت | `set_time_limit` در همان process بی‌اثر است. تنها راه: subprocess با سقف = کارایی فاجعه |
| حملهٔ زنجیره‌ای از توالی ۵ کلیک | با re-auth رمز عبور بسته می‌شود |

این را در UI هم باید نوشت. پنهان کردنش یعنی غافلگیر کردن کاربر.

# بخش ۲ — ساختار بسته

## درخت بستهٔ مجاز

```
بسته.zip
├── manifest.json          ← ⚠️ حتماً در ریشه. هویت + امضا
├── Laravel/               ← کد بک‌اند
│   ├── src/               ← ریشهٔ PSR-4
│   │   ├── ServiceProvider.php
│   │   ├── Http/Controllers/
│   │   ├── Services/
│   │   ├── Jobs/
│   │   ├── Models/
│   │   └── Policies/
│   ├── routes/api.php     ← فقط API
│   ├── database/migrations/
│   └── config/plugin.php  ← فقط مقادیر پیش‌فرض
└── Next.js/               ← توضیحات سطح UI
    ├── panel/             ← داده و دارایی
    └── blocks/            ← تعریف بلوک سایت
```

**دو نکتهٔ حیاتی:**

**۱. `manifest.json` باید در ریشه بماند.** اگر داخل `Laravel/` باشد، همهٔ آپلودها ۴۲۲ می‌شوند چون امضا یکپارچه می‌ماند ولی کد فعلی دنبالش در ریشه می‌گردد. پوشه‌های `Laravel/` و `Next.js/` فقط **قرارداد مسیر** هستند، نه محل مانیفست.

**۲. هر چیزی خارج از این درخت رد می‌شود** (deny-by-default). این عمدی است: اگر فهرست مجازها مثبت بود، هر پوشهٔ جدیدِ هسته یک ردیف جدید لازم داشت و فهرست‌های مرده جمع می‌شدند.

## مانیفست

```json
{
  "schema_version": 1,
  "slug": "blog",
  "name": "بلاگ پیشداد",
  "version": "1.0.0",
  "requires": { "core": ">=1.4.0 <2.0.0", "php": ">=8.2" },

  "entry": { "service_provider": "Pishdad\\Plugins\\Blog\\ServiceProvider" },
  "api": {
    "prefix": "blog",
    "middleware": ["auth:sanctum", "plugin.active"],
    "routes": "routes/api.php"
  },
  "db": { "table_prefix": "blog_", "migrations": "database/migrations" },
  "capabilities": ["db", "storage"],

  "panel": {
    "extensions": [
      { "point": "admin.menu", "key": "posts", "label": "نوشته‌ها", "href": "/admin/blog" }
    ]
  },

  "publisher": { "key_id": "a1b2c3…" },

  "signature": "base64…"
}
```

| فیلد | الزامی؟ | توضیح |
|---|---|---|
| `slug` | ✅ | ⚠️ باید `^[a-z0-9][a-z0-9._-]{1,39}$` باشد. **اگر فارسی باشد رشتهٔ خالی می‌شود** (باگ B2 که هنوز باز است) |
| `name` | ✅ | نام فارسی نمایشی |
| `version` | — | `1.0.0` |
| `requires.core` | — | ⚠️ **الان بررسی نمی‌شود** (باگ B25) |
| `panel.extensions` | — | فهرست نقاط اتصال |
| `publisher.key_id` | — | اثر انگشت کلید عمومی ناشر |
| `signature` | ✅ | امضای Ed25519 روی مانیفست بدون فیلد `signature` |
| `system` | ⛔ | **ممنوع.** پلاگین سیستمی فقط از allowlist می‌آید |

## سه مفهوم اعتماد که نباید قاطی شوند

پیش از این بازنویسی، این سه زیر یک نام (`signature_valid`) مخلوط شده بودند:

| # | مفهوم | چه چیزی را ثابت می‌کند | چه چیزی را **نمی‌گوید** |
|---|---|---|---|
| ۱ | **اصالت** | مانیفست از کلید خصوصی ناشر آمده | ناشر قابل‌اعتماد است یا نه |
| ۲ | **یکپارچگی** | فایل‌های روی دیسک همان‌اند که امضا شدند | کد هنگام نصب امن بوده |
| ۳ | **تأیید ما** | پلتفرم این نسخه را دیده و بررسی کرده (اداری) | **هیچ چیز رمزنگاریک** |

مدل قدیمی یک کلید واحد داشت، پس «امضا معتبر» عملاً یعنی «تأییدشده» — یعنی همان **تأیید** با لباس **اصالت**. با باز شدن مسیر آپلود محلی این مدل فرو می‌ریخت.

**جدا شدند:** `publisher_verified` (اصالت) · `review_status` (تأیید) · `content_digest` + `digest_verified_at` (یکپارچگی).

# بخش ۳ — چطور آپلود می‌شود (مرحله به مرحله)

## جریان فعلی — دقیقاً چه اتفاقی می‌افتد

```
کاربر فایل ZIP را انتخاب می‌کند
        ↓
POST /api/v1/admin/plugins/validate  (یا مستقیم upload)
        ↓
   ┌────────────────────────────────────┐
   │  مرحله ۱: ۱۱ کنترل روی فهرست ZIP │  ← هیچ چیزی استخراج نمی‌شود
   │            هیچ DB، هیچ فایلی     │
   └────────────────────────────────────┘
        ↓
   خطا؟ ──بله──→ ۴۲۲ + کل تحلیل در بدنهٔ پاسخ. نصب انجام نمی‌شود.
        ↓ خیر
   ┌────────────────────────────────────┐
   │  مرحله ۲: بررسی امضا از trust store│
   └────────────────────────────────────┘
        ↓
   ┌────────────────────────────────────┐
   │  مرحله ۳: ذخیرهٔ ZIP + ساخت رکورد │
   │            → review_status=pending  │
   └────────────────────────────────────┘
        ↓
   منتظر بازبینی
        ↓
    فعال‌سازی → پرمیشن‌های اعلام‌شده در مانیفست ساخته می‌شوند
```

## مرحله ۱ — ۱۱ کنترل (🟢 زنده)

همه **قبل از استخراج**، روی فهرست فایل‌های ZIP. دلیل: `ZipArchive::extractTo()` در برابر مسیرهای `..` محافظت کامل ندارد.

| # | کنترل | کد خطا | چه جلویی را می‌گیرد |
|---|---|---|---|
| ۱ | حجم ZIP ورودی | `zip.too_large` | بستهٔ غول‌پیکر |
| ۲ | تعداد فایل | `zip.too_many_files` | بمب |
| ۳ | حجم بازشده | `zip.bomb_size` | zip bomb |
| ۴ | نسبت فشرده‌سازی | `zip.bomb_ratio` | zip bomb |
| ۵ | مسیر ناامن | `path.unsafe` | **zip-slip**: مسیر مطلق، `..`، نام رزروشدهٔ ویندوز (`CON`, `NUL`, …) |
| ۶ | symlink | `path.symlink` | symlink-to-`/etc/passwd` |
| ۷ | مسیر تکراری | `path.duplicate` | نوشتن دوباره روی یک فایل |
| ۸ | تعارض حروف | `path.case_collision` | `A.php` و `a.php` روی فایل‌سیستم case-insensitive یکی می‌شوند — **برای کاربر ایرانی روی هاست ویندوزی یک باگ واقعی** |
| ۹ | مسیر خارج از بستهٔ مجاز | `path.not_allowed` | نوشتن در پوشه‌های هسته |
| ۱۰ | مانیفست جابه‌جا | `manifest.misplaced` | امضای بی‌اثر |
| ۱۱ | حجم بستهٔ مجاز | `package.large` | سرریز opcache |

### کنترل‌های مانیفست

| کد | چه می‌گوید |
|---|---|
| `manifest.missing` | مانیفست در ریشه پیدا نشد |
| `manifest.missing_field` | `slug` یا `name` نیست |
| `manifest.system_forbidden` | فیلد `system` در مانیفست هست |
| `manifest.leaks_key` | کلید رمزنگاری داخل بسته |

### کنترل‌های امضا و نقاط اتصال

| کد | معنی |
|---|---|
| `signature.invalid` | امضا معتبر نیست (یا ناشر ناشناخته/ابطال‌شده) |
| `signature.anonymous_publisher` | ⚠️ **هشدار** — امضا درست ولی ناشر اعلام نشده. با «تأییدشده» فرق دارد |
| `panel.unknown_point` | نقطهٔ اتصال ناشناخته + فهرست معتبر نمایش داده می‌شود |
| `panel.deferred_point` | نقطه در v1 پشتیبانی نمی‌شود + دلیلش |
| `panel.bad_point` | شکل آبجکت غلط |
| `hooks.not_yet_dispatched` | ⚠️ **هشدار** — فیلد `hooks` در قرارداد نیست: نه ثبت می‌شود نه اجرا. از مانیفست حذفش کنید |

## تجربهٔ کاربر — «این فایل کجا باید برود؟»

برای هر خطای مسیر، سیستم **محل درست را پیشنهاد می‌دهد**:

```
خارج از بستهٔ مجاز
فایل «Laravel/BlogPostController.php» در بستهٔ مجاز نیست.
با توجه به ساختار این فایل، احتمالاً باید در
«Laravel/src/Http/Controllers/BlogPostController.php» قرار بگیرد.
مسیر فعلی:  Laravel/BlogPostController.php
مسیر درست:  Laravel/src/Http/Controllers/BlogPostController.php
نام فایل به «Controller» اشاره دارد.
[راهنمای مرتبط]
```

منطق پیشنهاد **heuristic** است (بر اساس نام فایل و پسوند) و در UI باید «پیشنهاد» بنامی��د نه «الزام» — چون اگر اشتباه کند و UI بگوید الزام است، توسعه‌دهنده به کل راهنما بی‌اعتماد می‌شود.

## نکتهٔ صادقانه دربارهٔ این مرحله

این مرحله **کامل** است — یعنی می‌توانی همین الان یک بستهٔ خراب بدهی و دقیقاً بفهمی ایراد کجاست، بدون اینکه چیزی نصب شود. ولی **فقط ساختار** را می‌گوید، نه اینکه کد کار می‌کند یا نه. آن نیازمند اجرای واقعی است (فاز ۱).

# بخش ۵ — نقاط اتصال: چه می‌توانی اضافه کنی

## اصل حاکم

> هر نقطهٔ اتصال **دو چیز** دارد که الان هیچ‌کدام وجود ندارد:
> ۱. **schema مشخص** — دقیقاً چه فیلدهایی مجاز است
> ۲. **درجهٔ باز بودن** — عمداً بسته یا عمداً باز

## سه درجهٔ باز بودن

| درجه | معنی | مثال |
|---|---|---|
| `closed` | فقط فیلدهای ثابت. هیچ چیزی برای «باز کردن» نیست | `admin.menu` — خروجی‌اش `MenuItem` با ۴ فیلد ثابت است |
| `schema_defined` | نوع قفل ولی محتوا باز | `site.header_widget` — نوع ویجت را هسته رندر می‌کند، ولی `settings` از `block_type` خودِ پلاگین می‌آید |
| `open_vocabulary` | **پلاگین واژگان خودش را تعریف می‌کند** | `site.page_type` · `site.block_type` — خواستهٔ صریح تو |

## گرامر micro-schema

| مجاز | ممنوع | چرا ممنوع |
|---|---|---|
| `string` `integer` `number` `boolean` | `object` تودرتو | `SchemaForm.tsx:33` فقط یک map تفت را می‌چرخاند. `object` تودرتو نه فرم دارد نه رندر — نویسنده می‌نویسد، یک input متنی می‌بیند، یک بعدازظهر گم می‌کند |
| `enum` | `array of object` | همان |
| `media_id` `media_ids` | `$ref` · `oneOf` · `anyOf` | پیچیدگی بدون مصرف‌کننده |
| `richtext` (فقط با کلید `body`) | `format:uri` | `SchemaForm.tsx:95` روی کلید `body` شرطی است، نه روی `type` |
| | `patternProperties` | سطح حملهٔ بی‌استفاده |

# بخش ۶ — حالت توسعه‌دهنده

## چرا اصلاً وجود دارد

دو مسیر نصب:

| مسیر | کاربر | وضعیت | ریسک |
|---|---|---|---|
| **بازار** | کاربر عادی | 🔴 ساخته نشده | کم — پلتفرم بررسی می‌کند |
| **محلی** | برنامه‌نویس، پلاگین اختصاصی | 🔴 ساخته نشده | بالا — کد ناشناس |

مسیر محلی باید **بسته باشد** چون کد ناشناس روی سرور مشتری اجرا می‌شود.

## وضعیت واقعی: چه چیزی پیاده شده و چه چیزی نه

**دروازهٔ سمت سرور وجود دارد و کار می‌کند.** `GateDevModeUpload` روی هر دو مسیر
`plugins/upload` و `plugins/{plugin}/upgrade` فعال است (`routes/api.php:222,226`)
و ادعای «دسترسی توسعه‌دهنده» را فقط وقتی تأیید می‌کند که هدر
`X-Pishdad-Dev-Token` معتبر باشد.

> ⚠️ **اما راهی برای روشن‌کردن آن هنوز کامل نیست.** سرویس‌های بک‌اند کامل‌اند
> (`DevMode`، `DevModeTaps`، `DevModeUnlock`، `DevModeAudit`)، ولی **هیچ route ی
> برای ثبت کلیک یا unlock وجود ندارد** و **`DevModeGate`/`UploadGateNotice` در هیچ
> صفحه‌ای mount نشده‌اند**. یعنی `dev_mode` عملاً همیشه خاموش است و فقط بستهٔ
> **امضاشده** از فیلتر امضا رد می‌شود. این را `B37` دنبال می‌کند.

یعنی عملی: **آپلود مستقیم ZIP بدون امضا همیشه رد می‌شود**، ولی ادمین هیچ راهی
ندارد آن را فعال کند — که وضعیت fail-closed درست است، و گیت‌کردن دکمه در UI
هنوز انجام نشده.

## طراحی تأییدشده (هنوز اجرا نشدهٔ کامل)

```
۵ کلیک متوالی روی گزینهٔ حالت توسعه‌دهنده در تنظیمات
   ↓ (فاصلهٔ بیش از ۲ ثانیه ⇒ صفر)
مودال تأیید با رمز عبور  ← نه checkbox
   ↓
dev_mode = true, expires_at = now() + 8h
   ↓
ثبت در لاگ فعالیت نصب
   ↓
دکمهٔ آپلود + راهنما ظاهر می‌شود
```

| قاعده | چرا |
|---|---|
| شمارنده per-user + per-IP | اگر per-install باشد، یک صفحهٔ مخرب با یک POST ساده بازش می‌کند |
| وضعیت نهایی per-install | posture امنیتی آن سطح سایت است، نه ترجیح کاربر |
| **re-auth با رمز** | gesture پنج‌کلیکی سمت کلاینت است و در برابر CSRF ضعیف |
| انقضای خودکار ۸ ساعته | حالت توسعه‌دهندهٔ دائمی = دریچهٔ باز دائمی روی هر نصبی که یک بار فعالش کند |
| لاگ کامل | بعد از نصب یک پلاگین بد، همین ردپا تفاوت «می‌توانیم عیب‌یابی کنیم» و «کور هستیم» است |

## چه چیزی در حالت توسعه‌دهنده باز می‌شود

| مسیر | وضعیت |
|---|---|
| دکمهٔ آپلود پلاگین محلی | ✅ باز |
| صفحات راهنمای ساخت پلاگین/قالب | ✅ باز |
| مشاهدهٔ manifest و فهرست فایل | ✅ باز |

## هشدار «تأییدنشده» — قابل دور زدن **نباید** باشد

دلیل: هشداری که قابل دور زدن باشد، کاربر را آموزش می‌دهد که بدون خواندن کلیک کند — و دقیقاً ارزشش را برای ۹۵٪ کاربرانی که پلاگین تأییدنشده نصب نمی‌کنند نابود می‌کند.

**حالت توسعه‌دهنده فقط «دسترسی» را باز می‌کند، نه «مصونیت» را.**

سه نقطهٔ نمایش: نشان کهربایی در فهرست · مودال با checkbox اجباری و نام ناشر · بنر ماندگار در صفحات خودِ پلاگین.

متن باید صادقانه باشد: «تأیید فنی نشده» یعنی *ما بررسی نکرده‌ایم*، نه «ناامن است».

# بخش ۸ — پلاگین چه کارهایی می‌تواند بکند

## ۱. API

```
/api/v1/p/{slug}/…
```

| ویژگی | چرا |
|---|---|
| **یک** route واقعی در کل هسته | `PluginRouter` catch-all. بقیه همه داخلش dispatch می‌شوند |
| تداخل نام ساختاری ناممکن | چون تنها route مالک هسته است |
| `route:cache` معتبر می‌ماند | نصب پلاگین = یک فلگ در فایل cache، نه rebuild |
| غیرفعال‌سازی فوری | یک فلگ |

**چرا catch-all و نه route واقعی با prefix؟**

| گزینه | مشکل |
|---|---|
| route واقعی با `prefix()` | **در لاراول `prefix()` فقط متن URL را عوض می‌کند، محدوده نمی‌سازد.** یک پلاگین مخرب می‌تواند `Route::get('/v1/admin/users')` بزند و هسته را hijack کند |
| route واقعی | `route:cache` اپ را یک‌بار boot و serialize می‌کند. نصب پلاگین = `route:clear && route:cache` که روی هاست بدون SSH ممکن نیست |
| **catch-all** ✅ | هر دو مشکل حل می‌شود |

**میدلورها:** پلاگین **هرگز کلاس میدلور ثبت نمی‌کند** — فقط رشته اعلام می‌کند و هسته از registry بسته resolve می‌کند. چون اگر پلاگین به service container کامل دسترسی داشته باشد، می‌تواند هر singleton هسته را mutate کند و مرز امنیتی اصلاً شکل نمی‌گیرد.

## ۲. دیتابیس

```sql
CREATE TABLE blog_posts (...);   -- prefix اجباری: {slug}_
```

| قاعده | چرا |
|---|---|
| پیشوند اجباری | حذف پلاگین = drop زنجیره‌ای. و `DROP TABLE users` مسدود می‌شود |
| حداکثر ۲۰ جدول | سقف منابع |
| حداکثر ۱۰ ایندکس در هر جدول | همان |
| `^[a-z0-9_]+$`، حداکثر ۴۰ نویسه | نام‌های غیرقابل‌کنترل مسدود |
| بررسی تداخل با جدول‌های هسته | وگرنه پلاگین می‌تواند جدول هسته را劫ب کند |

**⛔ `CREATE DATABASE` واقعی رد شد.** یک DB دوم = pool دوم + backup دوم + ردیابی migration دوم، و وعدهٔ محصول «یک `docker compose`» را می‌شکند.

**⚠️ محدودیت باقی‌مانده:** اگر پلاگین بتواند `DB::statement('DROP TABLE users')` بزند، از همهٔ قوانین نام‌گذاری رد می‌شود. **تنها راه بستن واقعی، دو نقش PostgreSQL است:** `pishdad_owner` برای `migrate`، `pishdad_app` برای runtime با DDL فقط روی `{slug}_*`. آن‌وقت دیتابیس خودش جلویش را می‌گیرد. 🔴 هنوز ساخته نشده.

## ۳. رابط کاربری — فقط اعلانی

پلاگین **نمی‌تواند** هیچ کدی در مرورگر بگذارد. فقط **اعلام می‌کند** چه می‌خواهد، هسته رندر می‌کند:

| چه چیزی | چطور |
|---|---|
| منو | `admin.menu` → merge روی props سرور |
| ویجت هدر/فوتر | `site.header_widget` → از روی schema |
| بلوک صفحه | `site.block_type` → `BlockRenderer` از روی schema |
| صفحهٔ اختصاصی | `admin.page_registry` → `SchemaForm` + page descriptor |
| فرم تنظیمات | `admin.settings_schema` → `SchemaForm` |
| جدول داده | `admin.data_collection` → `DataTable` + `Pagination` |
| کادر ابزار در هدر | `admin.plugin_tools` → drawer |

**نکتهٔ مهم:** نیمهٔ بک‌اندی نیمی از اینها از قبل نوشته شده — `widgetSchemas()`، `pageTypes()`، `DashboardController::widgets()`، و کامپوننت `SchemaForm` همین حالا وجود دارد.

# بخش ۹ — چرخهٔ حیات

## وضعیت‌های بازبینی

| وضعیت | معنی | کی می‌گیرد |
|---|---|---|
| `unverified` | 🟢 **پیش‌فرض** | هر پلاگینی که از مسیر بازار نیامده |
| `pending` | در انتظار بررسی | پلاگین آپلودشدهٔ محلی |
| `approved` | تأیید فنی شده | بازبین تأیید کرد |
| `rejected` | رد شده با دلیل ثبت‌شده | بازبین |

> ⚠️ **پیش‌فرض قبلاً `approved` بود** یعنی هر مسیر کدی که این فیلد را ست نمی‌کرد (seeder، `forceFill`، مسیر آیندهٔ بازار) خودکار روی «تأییدشده» می‌افتاد. **fail-open.** فاز ۰ اصلاحش کرد.

## چرخه

```
آپلود → تحلیل ساختار → بررسی امضا → pending → فعال → ارتقا → غیرفعال → حذف
                                              ↓
                                          رد (با دلیل)
```

## بازگشت به عقب — هنوز ممکن نیست

`upgrade()` الان فایل قبلی را **قبل از موفقیت جدید** حذف می‌کند. یعنی:
- اگر دیسک پر باشد ⇒ پلاگین فعال با `path` به فایل ناموجود ⇒ آجر
- rollback فقط یک رشتهٔ `previous_version` است **بدون آرتیفکت**

ساختار درست: `releases/{version}-{hash}/` + اشاره‌گر `current`. تعویض = یک rename اتمیک.

# بخش ۱۰ — مهر یکپارچگی

## چیزی که خواسته بودی و چرا نباید همان‌طور باشد

خواسته: «هر پلاگین یک کلید عمومی بگیرد و نصب باید با فایل‌های آپلودشده مطابقت کند.»

اگر منظور **کلیدی باشد که داخل آرتیفکت قرار بگیرد، بی‌معنی است** — کلید عمومی کنار چیزی که امضا می‌کند، مثل گذاشتن مهر کنار خود سند. هرکس بتواند آرتیفکت را تغییر دهد، کلید را هم عوض می‌کند.

## چیزی که واقعاً کار می‌کند: مهر یکپارچگی per-install

کلید تصادفی ۳۲ بایتی **در لحظهٔ نصب، روی سرور خود کاربر** تولید می‌شود. نیمهٔ خصوصی بیرون از آرتیفکت (جدول `settings`)، نیمهٔ عمومی در `manifest.lock.json`. یک re-seal در هر boot یا هر N دقیقه، digest فعلی فایل‌ها را امضا و با نیمهٔ عمومی مقایسه می‌کند.

| تضمین می‌کند | تضمین **نمی‌کند** |
|---|---|
| فایل‌های روی دیسک همان‌اند که در لحظهٔ نصب بودند | اینکه کد هنگام نصب امن بوده |
| دست‌کاری بعدی تشخیص داده می‌شود | اینکه پلاگین از ناشر واقعی آمده |
| استخراج ناقص/دانلود قطع‌شده تشخیص داده می‌شود | اینکه کد آسیب‌پذیری ندارد |
| replay یک آرتیفکت قدیمی‌تر تشخیص داده می‌شود | اینکه کاربر «تأییدنشده» بودن را دیده |

کلید **باید per-install و بیرون از آرتیفکت باشد.** اگر داخل ZIP باشد، uninstall + نصب مجدد همان ZIP آن را بی‌اثر می‌کند.

**برای UI:** «کلید عمومی» ننامید. «مهر یکپارچگی» یا «اثر انگشت نصب». اگر به کاربر «کلید عمومی» بگویی، انتظار امنیتی می‌سازی که برآورده نمی‌شود و بعداً به‌عنوان باگ امنیتی علیه‌ات استفاده می‌شود.

**برای پلاگین بازار، اصالت + یکپارچگی با یک امضا حل می‌شود:** چون `content_digest` داخل مانیفست امضاشده است، امضای Ed25519 گذرا کل payload را پوشش می‌دهد.

## الگوریتم digest

```
sha256. الگوریتم‌های دیگر رد شدند:
MD5/SHA-1 (شکسته) · SHA-512 (فایده ندارد)
BLAKE3 (برای PHP binding نگه‌داری‌شده ندارد و به کامپایلر نیاز دارد —
        برای CMSی که روی هاست نصب می‌شود غیرقابل دفاع)

۱. فهرست فایل‌ها، هر ورودی نرمال‌شده (جداکننده → '/')، بدون case-fold
۲. برای هر فایل به‌جز manifest.json: digest_file = sha256(محتوا)
۳. مرتب‌سازی بایتی (strcmp)، ساخت خطی:
     "<relpath>\0<8-hex از mode>\0<digest_file>\n"
۴. files_digest = sha256(concat خطوط)
۵. manifest بدون فیلد signature → canonical JSON → manifest_digest
۶. content_digest = sha256("pishdad-digest-v1\0" + manifest_digest + "\0" + files_digest)
```

- **`manifest.json` از فهرست بیرون است** چون خودش امضا دارد. اگر داخل باشد circular می‌شود.
- **prefix نسخه‌دار** تضمین می‌کند تغییر الگوریتم digest قبلی را بی‌صدا بی‌اعتبار نکند.
- **بدون نرمال‌سازی** یک ZIP می‌تواند همان کد را `./src/A.php` و `src/A.php` بگوید و دو digest متفاوت بدهد، در حالی که PSR-4 هر دو را یکی می‌بیند.

🔴 **هنوز پیاده نشده.** `ensureSealKey()` نوشته شده ولی هیچ caller ندارد.

# بخش ۱۱ — بازار

## مدل داده

`publishers` · `market_items` · `market_versions` · `licenses`

**نکتهٔ کلیدی:** امضا باید روی `market_versions` باشد، نه `market_items`. امضا برای یک **نسخهٔ مشخص** از کد معنی دارد.

## وضعیت‌ها

| وضعیت | نشان | معنی |
|---|---|---|
| `pending` | خاکستری/کهربایی | در انتظار بازبینی |
| `approved` | سبز | تأیید فنی شده |
| `rejected` | قرمز | رد شده با دلیل |
| `unverified` | کهربایی | **محلی**، هرگز بازبینی نشده |
| **`yanked`** | قرمز | ⚠️ **غیرقابل حذف** — بعد از incident امنیتی |
| `deprecated` | زرد | کار می‌کند ولی توصیه نمی‌شود |

**چرا `yanked` غیرقابل حذف است:** بدون آن، یک پلاگین آسیب‌پذیر با هزار نصب فقط با «حذف از بازار» از دسترس خارج می‌شود — ولی هزار نصب فعال همچنان اجرایش می‌کنند و هیچ اطلاعی نمی‌گیرند. `yanked` اجازه می‌دهد به نصب‌های فعال **push** کنی.

## مدل لایسنس

**چه چیزی خریداری می‌شود:** حق اجرای کد روی N نصب. **نه** کلید لایسنس به سبک وردپرس.

| گزینه | ارزیابی |
|---|---|
| دائمی، نامحدود نصب، بدون phone-home | ساده و صادقانه، ولی قابل دزدی |
| دائمی + فعال‌سازی با phone-home | **مسئلهٔ برند:** بلاک کردن سایت در حال کار به‌خاطر قطعی سرویس غیرقابل دفاع است |

**توصیه:** لایسنس دائمی، نصب نامحدود، بدون phone-home مسدودکننده. **اهرم اصلی قیمت نیست؛ سازگاری است.** وقتی آپدیت‌ها تا وقتی هسته زنده است رایگان‌اند، توسعه‌دهنده انگیزهٔ هم‌راستایی با پایداری هسته پیدا می‌کند.

# بخش ۱۲ — چه چیزی در هسته است و چه چیزی نباید باشد

## قاعده

> **اگر حذف پلاگین، توانایی استفاده از سایت عمومی را از کار بیندازد، آن فایل در هسته است.**

نتیجهٔ منطقی: پلاگین هرگز نباید وابستگی سختِ سایت عمومی باشد. وقتی هسته باید رفتاری
اختیاری را صدا بزند، الگو یک **interface متعلق به هسته با پیش‌فرض بی‌خطر** است و
پلاگین implementation خودش را از راه `core.service_provider` ثبت می‌کند:

```
هسته:    یک interface که هسته تعریف می‌کند
پیش‌فرض: یک پیاده‌سازی بی‌اثر که هیچ جدولی نمی‌خواند و چیزی را تغییر نمی‌دهد
پلاگین:  پیاده‌سازی خودش را از راه core.service_provider ثبت می‌کند
```

نبودِ پلاگین = سایت کار می‌کند، با همان پیش‌فرض. فهرست interfaceهای قابل ثبت بسته و
کوچک است (`PluginPackageContract::OVERRIDABLE_INTERFACES`)؛ provider جستجو
(`App\Search\SearchableProvider`) نمونهٔ مرجع آن است.

## زنده یا ثابت؟ — هر دو، تقسیم‌شده

| بخش | منبع | چرا |
|---|---|---|
| مرجع فیلدهای مانیفست | **زنده** (از قرارداد) | نمی‌تواند drift کند |
| نام پرمیشن‌های تولیدشده | **زنده** (از مانیفست‌های فعال) | همان منطق `GET /admin/permissions` |
| نکات و best-practice | **ثابت** | نیاز به قضاوت انسانی دارد |
| CLI اسکلت‌ساز | **کد** | بهترین راهنما، راهنمایی است که خودش پروژه می‌سازد |

**چرا «کاملاً زنده» غلط است:** راهنمایی که از روی کد تولید می‌شود دلیل و تصمیم ندارد. توسعه‌دهنده می‌پرسد «چرا `src/` و نه ریشه؟» و جواب «چون فایل منتوی همین است» جواب نیست.

**چرا «کاملاً ثابت» غلط است:** راهنمای ثابت بدون owner در سه ماه دروغ می‌گوید. نشانه: راهنمای فعلی `DeveloperGuide.tsx` سه خطای محتوایی دارد — ساختار ZIP قدیمی، فیلد `system` که حذف شد، و یک کلید هاردکد به‌جای trust store. **یعنی الان به کاربر دستور غلط می‌دهد.**
